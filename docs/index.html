The open-source hosting control panel for Ubuntu. Install it on a fresh server with one command, then create and host websites from a web panel — each with its own Apache virtual host, isolated PHP-FPM pool, MySQL database and optional Let's Encrypt certificate.

What it does

Provision a real site, without touching the command line

Everything below is in the v0.1 source today. Nothing here is a plan.

Per-site isolation

Every site gets its own MySQL database and user, its own PHP-FPM pool on a dedicated unix socket, and its own Apache vhost. The pool sets open_basedir to the site's docroot, so one site cannot read another's files.

A tiny privileged surface

The panel runs as an unprivileged user and never runs arbitrary shell. It can invoke exactly three root-owned verbs — site_create, site_delete, site_list — through a sudoers allowlist, and each one re-validates every argument it is given.

Let's Encrypt, when DNS is ready

Tick the SSL box and the runner checks that the domain actually resolves to this server before calling certbot. If it does not, the site still comes up on port 80 and the job reports ssl=skipped_dns rather than failing.

Async jobs with live status

Create and delete run as background jobs. The panel persists each one, polls its status, and shows you the runner's result. Identical in-flight jobs for the same domain are de-duplicated instead of racing each other.

Ordinary, portable config

No exotic runtime and no proprietary format. What Hostzilla writes is plain Apache, PHP-FPM and MySQL configuration you could have written yourself — and you can read every byte of it before you install, in the demo below.

Rolls back a failed create

Each provisioning step registers an undo action. If a later step fails, the earlier ones are reversed, so a failed create leaves no half-provisioned docroot, database or pool behind to block the retry.

Interactive demo

Read it before you run it

Know exactly what lands on your server

Most control panels are a black box: you point an installer at a clean machine and hope. Hostzilla writes plain, boring config — and the demo above generates it for you, for your domain, before you have installed anything.

Create a site in the demo and open View generated config. You get the Apache vhost, the PHP-FPM pool, the MySQL statements, the site manifest and the starter content, each with the path it would be written to and a copy button.

Those templates are ported line for line out of runner/site_create.sh and runner/_lib.sh, and the port is checked against the shell by generating both and diffing the bytes. The database identifier is even derived with the same truncate-and-SHA-256 scheme, so the name you see in the demo is the name you will get.

/etc/apache2/sites-available/<domain>.conf 
<VirtualHost *:80>
    ServerName demo.example.com
    DocumentRoot /var/www/demo.example.com
    DirectoryIndex index.php index.html
    <Directory /var/www/demo.example.com>
        Require all granted
        AllowOverride All
        # No directory listings — an empty or partially uploaded site must not
        # expose a browsable file index.
        Options -Indexes +FollowSymLinks
    </Directory>
    # Never serve dotfiles: .git, .env and friends routinely leak credentials.
    # .well-known stays reachable so ACME http-01 renewals keep working.
    <FilesMatch "^\.">
        Require all denied
    </FilesMatch>
    <DirectoryMatch "/\.(?!well-known)">
        Require all denied
    </DirectoryMatch>
    <FilesMatch \.php$>
        SetHandler "proxy:unix:/run/php/hz-demo.example.com.sock|fcgi://localhost"
    </FilesMatch>
    ErrorLog  ${APACHE_LOG_DIR}/demo.example.com-error.log
    CustomLog ${APACHE_LOG_DIR}/demo.example.com-access.log combined
</VirtualHost>
The privilege boundary

Three verbs, and nothing else, may become root

A hosting panel is a web application that configures a server as root. That seam is the whole security story, so Hostzilla makes it as small as it can be and writes it down.

How a request reaches root

  1. The Flask panel runs as the unprivileged hostzilla user.
  2. It validates the domain and the site type, then queues a job.
  3. The job calls sudo /opt/hostzilla/runner/<verb>.sh with positional arguments. No shell string is ever assembled.
  4. Sudoers permits those three scripts and nothing else, with env_reset so no HZ_* variable can be smuggled in.
  5. The verb re-validates every argument, refuses protected domains, and prints a single JSON line that the panel parses.

The runner also refuses to clobber an existing docroot, and delete only ever removes a site that has a manifest the runner itself wrote — so it can never take out a site that was already on the machine.

config/sudoers.hostzilla 
# The "hostzilla" service user may run ONLY the three provisioning
# verbs below, NOPASSWD, and nothing else.
Defaults:hostzilla env_reset

hostzilla ALL=(root) NOPASSWD: /opt/hostzilla/runner/site_create.sh *, \
                               /opt/hostzilla/runner/site_delete.sh *, \
                               /opt/hostzilla/runner/site_list.sh

What each verb is allowed to do

The complete set of privileged operations in Hostzilla v0.1.
VerbArgumentsEffect
site_create.sh <domain> static|php|wordpress [--ssl] Creates the docroot, MySQL database and user, PHP-FPM pool, starter content, root-only manifest and Apache vhost; reloads PHP-FPM and Apache; optionally runs certbot. Undoes every step if one fails.
site_delete.sh <domain> [--purge-db] Removes the vhost, the pool, the docroot and the manifest, and optionally drops the database and user. Refuses any domain with no Hostzilla manifest.
site_list.sh (none) Read-only. Prints the sites recorded in /etc/hostzilla/sites as JSON. Never mutates anything.
Install

One command on a clean box

The installer provisions Apache, PHP-FPM, MySQL and certbot, installs the panel under gunicorn and systemd, creates the unprivileged hostzilla service user, places the sudoers allowlist, and prints your dashboard URL and a freshly generated admin password when it finishes.

You need

  • A fresh Ubuntu 22.04 or 24.04 server — a clean VPS or VM is ideal.
  • root access; the installer configures system services.
  • A public IP, and for SSL a domain whose DNS you can point at the server.

Run Hostzilla on a dedicated host. The installer assumes it owns Apache, PHP-FPM and MySQL on the machine.

install 
git clone https://github.com/iampopye/hostzilla.git
sudo bash hostzilla/install.sh
where things land
/opt/hostzilla/            # panel + runner
/etc/hostzilla/hostzilla.conf  # config
/etc/hostzilla/sites/      # per-site manifests (root, 0600)
/var/lib/hostzilla/hostzilla.db # panel database
/var/log/hostzilla/        # installer + runner logs
/var/www/<domain>/         # your sites

Status

Hostzilla is v0.1 — here is exactly where it stands

So you can decide whether it is useful to you today, rather than finding out after you have installed it.

Works now

  • One-command install on a fresh Ubuntu 22.04 / 24.04 server
  • Create static, PHP and WordPress sites from the dashboard
  • Per-site Apache vhost, PHP-FPM pool, MySQL database and user
  • Optional Let's Encrypt certificate when DNS already points at the server
  • Delete a site, including its database
  • Async job queue with live status and logs
  • Change your panel password

Not built yet

  • Visual / drag-and-drop site builder
  • Email hosting, DNS management, backups
  • Multiple panel users, reseller accounts, billing
  • nginx support — Apache only
  • Editing a site after creation, beyond deleting and recreating it

No part of the panel does these today.

Known limits

  • One operator account. There is no user management UI.
  • The panel assumes it owns Apache, PHP-FPM and MySQL on the machine.
  • The login throttle is per worker process, not cluster-wide.
  • install.sh targets Ubuntu specifically; other distributions are untested.
